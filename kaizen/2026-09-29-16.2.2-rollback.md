## Why 2: Why does production differ from the recorded 16.2.2?

Because production is not the build the harness recorded. The recording is the signed image
`quay.io/tutors-sdk/tutors-reader:16.2.2` (digest `sha256:7567d59…`, created 2026-09-19T18:07Z from `caa53d0`).
tutors.dev was built at 2026-09-18T08:06Z, three minutes after the release PR
[#264](https://github.com/tutors-sdk/tutors-mono-repo/pull/264) merged `caa53d0` (08:03Z), by Netlify from source
(`apps/reader/netlify.toml`: `pnpm --filter tutors-reader... build`). Same commit, a different build and a
different host, so the two can differ without any change to the code.

## Why 3: Why is production built outside the image the harness gates?

Because the deploy path that ships the gated image is built but does not serve tutors.dev yet. The monorepo's
`deploy.yml` pins signed digests into `deploy/k8s/overlays` and `release/deployed.json` (16.2.2, deployedAt
2026-09-21T10:57Z) for OpenShift, and the OpenShift and AWS migration that would make those overlays production is
planned, not done. So the "deployed" dispatch that tells the harness what production serves has never been sent:
none of the 64 runs was a `repository_dispatch`, every judged one was the 15-minute schedule.

## Why 4: Why has a red check not stopped anything for twelve days?

Because the release SOP has no step that says which build production serves before post-deploy is trusted. The
monitor finds the same five differences every quarter hour, the rollback issue deduplicates them by signature, and
a standing difference with no confirmed build reads as a standing alarm rather than a stop. The Jidoka rule holds
for the gate before a release; after it, nothing in the standard work says what to do when production is not the
tested artefact.
