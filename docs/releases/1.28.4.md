# Harness 1.28.4 (contract 1.28.4)

Post-deploy mode applies claims: `post-deploy/claims.yaml`. The contract changelog entry is in
[../contract.md](../contract.md#changes). A **patch**: no input, output field, verdict, exit code,
claims key or flag changes, and no mask.

## Why

The synthetic monitor has failed every run since the nightly A/A came back clean, and commented on
rollback issue #38, on five differences that are understood. tutors.dev serves an unnamed build made
2026-09-18T08:06:22Z (`/_app/version.json`, no `/version`), not the 16.2.2 images the recorded release
run tested: its Supabase project has no `app_errors` table, and its pages are the older course shell.
The next release, deployed from the monorepo, replaces that build.

`post-deploy.yml` ran post-deploy mode with no `--claims`, so there was no way to say "known, explained,
until the next release": only a mask (which hides a difference for good, on every side) or a fix in
production. The release's own `claims.yaml` is the wrong file to read here: its claims excuse what a
candidate changed against production, not what production changed against the tested release, and it
is reset when a release branch is cut.

## What is new

- `post-deploy/claims.yaml`, read by `post-deploy.yml` (`--claims post-deploy/claims.yaml`) and by
  `harness local watch`. Same format and matcher as any claims file. Normally `claims: []`.
- It starts with five narrow claims, each with `until: "16.2.3"` and a reason naming issue #38:

  | artefact | scope | what it explains |
  |---|---|---|
  | `console` | `reference:course` | `404` from `/rest/v1/app_errors` |
  | `console` | `reference:lab` | `404` from `/rest/v1/app_errors` |
  | `console` | `reference:note` | `400` from `/rest/v1/app_errors` (the unload flush's `?Prefer=return=none`, mono-repo #353) |
  | `focus` | `reference:course` | no skip link or header buttons |
  | `network` | `GET {{course}}/course.png` | the older shell requests the course image on the lab page |

  In post-deploy mode side a is the recorded release, so `until: "16.2.3"` expires as soon as the
  recorded run is any release after 16.2.2. Lifetimes are informing until 2.0: an expired claim is
  reported and still covers, so remove these once they are stale.
- A console claim covers any new console message on its page, since a claim matches artefact and scope,
  not the message: a different new error on those three pages would be hidden until the claims go.
- `post-deploy/**` is an engine path: a change to the claims bumps the harness version and re-runs the
  mutants.
- A post-deploy report's "Unclaimed differences" points at `post-deploy/claims.yaml`.
- `tests/post-deploy-claims.test.ts` holds the file: it parses, every claim is narrow and has an `until`
  and an issue in its reason, the five differences of the 2026-10-03 run are all claimed and nothing else
  near them is, the lifetime is live against a 16.2.2 recording and expired against 16.2.3 and 16.3.0,
  and both the workflow and the local watch pass the file.
