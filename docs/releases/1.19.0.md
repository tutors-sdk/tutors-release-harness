# Harness 1.19.0 (contract 1.19.0)

Release size under control. Nothing said how big a release of the monorepo usually is, or when
the batch waiting on `main` had grown past it: on 30 September main held 68 merged PRs that
production did not, more than six times the largest of the last six releases. The overnight
readiness page now opens with a **control chart** of release sizes and a **WIP limit** on what
is waiting, so maintainers see the batch approaching the point where it should be released. The
contract changelog entry is in [../contract.md](../contract.md#changes). A **minor** release,
because `harness readiness` takes `--releases` and `--fetch-releases`: no verdict, Gate, exit
code or `report.json` field changes, and the chart is never an input to any of them.

## What is new

- **The control chart**, at the top of `readiness.html`. Each point is one past release (a plain
  `vX.Y.Z` tag of the monorepo) in **merged PRs** since the release before it, counted on the
  first-parent line as `harness changes` counts them: release branches and direct commits left
  out. It is an XmR (individuals) chart: **centre line** = the mean; **UCL** = mean + 2.66 × the
  mean moving range; **LCL** = max(0, mean − 2.66 × the mean moving range). A release outside
  the limits is ringed and named as a **special cause**.
- **The WIP limit** on the PRs on `main` not yet released, drawn as a diamond after the last
  release, its zone always written in words beside its colour: **below the centre line** (keep
  merging), **a good time to release** (above the centre line, within the WIP limit), **release
  now** (over it). The WIP limit is the UCL.
- **Provisional limits.** With fewer than 10 releases the limits are labelled provisional and
  the WIP limit is the centre line, so a short history never licenses a big batch.
- **Night by night**: the unreleased count from each kept forecast's `changes.json` against the
  same lines, so the climb is visible before the limit is crossed.
- On real data at release: the six releases v16.1.5 to v16.2.2 held 6, 1, 8, 5, 11 and 4 PRs.
  Centre 5.8, mean moving range 5.6, UCL 20.7, LCL 0, provisional (6 of 10). Main held 68 PRs
  since v16.2.2: **release now**, and above the UCL.
- **`releases.json`**: the release history, read from GitHub once per build of the pages by
  `harness readiness --fetch-releases` (the monorepo's tags and a compare per pair of releases;
  GET only) and kept in the site beside `readiness.json`, so the page is never drawn from the API
  per view. `--releases f` reads one. What GitHub did not answer is listed in its `errors`; a
  release it could not count is left out, never guessed. Without it, the page draws the batch
  from the newest forecast with no limits and says why.
- **`release-control.schema.json`** describes `control` in `readiness.json` and `releases.json`.
- Accessible: a text alternative on each chart, a table of every number, the zone in words,
  a wide and a narrow drawing so it reads at 375px without sideways scrolling, light and dark.

## Upgrading

Nothing to do. `pages.yml` passes `--fetch-releases` with the job's token, which already reads;
no new permission, job or artifact. To build it locally:
`pnpm harness readiness --site _site --fetch-releases` with `GITHUB_TOKEN` or `GH_TOKEN` (behind
an HTTPS proxy also `NODE_USE_ENV_PROXY=1`). How to read the chart is in
[the user guide](../user-guide/10-running-a-release.md#when-to-cut-the-release-size-control-chart).
