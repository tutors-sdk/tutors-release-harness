# Harness 1.58.0 (contract 1.57.0)

The signed-in journeys reach main again after mono-repo #327. This is a **minor** release: the journeys and the stack change, and nothing in the engine does.

## Why

The 28 Oct forecast (`sha-d350404` beside 17.0.0, [run 40617898562](https://github.com/tutors-sdk/tutors-release-harness/actions/runs/40617898562)) failed 11 signed-in journeys on side b only, all five runs, which made about 90 of the night's 166 unclaimed differences. The A/A was clean, so this was not noise. Mono-repo #327 (the data API seam, carrying #320) moved the browser's reads and writes to the reader's `/api` routes, and the harness had three expectations of the old shape:

1. **The sign-in wait (9 journeys).** `signInFromAuthPage` waited for the reconnect's last read, `GET /rest/v1/tutors-connect-users?select=online_status`. Main reads the same thing with `GET /api/me`, once for the sentiment and then once for the online status, so the wait timed out after 30 s ("page.waitForResponse: Timeout 30000ms").
2. **Course ids with a port.** The reader's data routes validate the course id and refuse `localhost:8080` (400), and `/api/courses/visit` reads the course's title from `https://<id>.netlify.app/tutors.json`. A production course id is a Netlify site, so on b no page view or visit was ever recorded (`RPC record_page_view` 2 on a, 0 on b).
3. **The time app (2 journeys).** Main's time app reads `/api/time/<course>` from the reader with the reader's session (`PUBLIC_READER_URL`, `PRIVATE_API_ALLOWED_ORIGINS`), so a lecturer who has not signed in never sees the PIN dialog ("locator.fill: Timeout 30000ms").

17.0.0 does none of this, so side a was never affected.

## What changed

- `traffic/journeys/ui.ts`: `onlineStatusRead()` accepts the Supabase read (17.0.0) or the second `GET /api/me` (main).
- `traffic/journeys/fixture.ts`, `rules.ts`, `journeys.ts`: every signed-in journey names its course by a Netlify site id. The fixture course is `harness-fixture` (`student-signs-in` and the fixture-course Rule journeys), and `@course-rules` reads `harness-rules` as `@course-site` already did. Anonymous journeys keep `localhost:8080`.
- `src/collectors/browser.ts`: `courseSites()` lists both sites, and the browser is answered for them in every signed-in journey, not only the Rule journeys.
- `fixtures/identity/stub.mjs` + `compose.harness.yaml`: the stub also answers `harness-fixture.netlify.app` from `FIXTURE_COURSE_ORIGIN` (`http://course:8080`), the signed-in readers resolve it, and the server certificate gains the name (re-signed with the committed test CA).
- `compose.harness.yaml`: the signed-in readers allow their side's time app (`PRIVATE_API_ALLOWED_ORIGINS`), and the time apps read from their side's signed-in reader (`PUBLIC_READER_URL`). 17.0.0 ignores both.
- `lecturer.feature`: the time journeys (Rules 0590, 0591) are `@course-site`. The lecturer signs in from the course first, then the seed goes in, and `the persistence stub holds the seed` lets the sign-in's last writes settle and drops its requests (`forget`) first.

Pages of the signed-in journeys are now `/course/harness-fixture/...` on both sides, where they were `/course/localhost:8080/...`, so the first forecast after this one shows them as new and gone in its delta. No verdict, Gate or exit code rule moves.
