# Harness 1.50.0 (contract 1.50.0)

A base image not pinned by digest is an image-hardening finding. A **minor**. Part of the harness hardening plan (production-readiness additions, tranche 1, item D4).

## Why

1.49.4 was the second time a base image moved under the same commit: Docker Hub moved `node:22-bookworm-slim` between two builds of main, and the forecast had 8 differences that no PR could declare. 1.49.4 stopped blaming an unrelated PR for them; nothing said why the move could happen at all. A base named by digest moves only in a PR, which can declare it.

## What changed

- `src/compare/policy.ts`: `hardening()` reads the base the manifest engine already collects (`org.opencontainers.image.base.name` and `.base.digest`, `docker image inspect`). A base named by a tag is `<app>/floating-base`; an image with no base name is `<app>/unrecorded-base`. A `base.digest` without a pinned name is not a pin, because a build resolves a tag to a digest too; the finding says what the tag resolved to on this build.
- `<app>/summary` says which base it read: `base pinned by digest (…)`, `base <name>` or `base not recorded`.

Each finding says, as the family always has, whether production has it too.

## What it means for the monorepo

Today's images record no base name, so every forecast will carry `unrecorded-base` on all four apps, "(production too)", until the Dockerfile does both: `FROM` the base by digest (`ARG NODE_IMAGE=docker.io/library/node:22-bookworm-slim@sha256:…`) and name it, either by BuildKit's own label or explicitly with `LABEL org.opencontainers.image.base.name="${NODE_IMAGE}"` in the runtime stage.

## Level

Informing, like the rest of the policy family: reported, claimable, never gates. No verdict, Gate, score or exit code moves.
