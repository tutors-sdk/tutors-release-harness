# Harness 1.25.0 (contract 1.25.0)

Soak prep. 2.0, the go-live release, waits on ten consecutive clean nights and on every check it
may make blocking having a planted mutant that it catches. This release builds everything that can
be built before the nights are counted, so the count starts on the night of **2 October 2026** and
nobody has to work it out by hand. The contract changelog entry is in
[../contract.md](../contract.md#changes). A **minor** for three new mutant kinds, one new finding and
one optional field. **No engine level changes and nothing new gates**: the policy checks stay
informing, and the a2 stack is reported, never judged.

## What is new

- **A planted mutant per policy check.** `mutants/mutants.yaml` now has thirteen mutants. The three
  new ones each plant the fault one policy check is there to find:
  - `secret-env`: the production image plus `ENV HARNESS_PLANTED_API_TOKEN=...` (a harmless fixed
    value under a name that says it is a secret), for **image hardening**;
  - `vulnerable-package`: the manifest of `ejs` 3.1.6 (a critical advisory, fixed in 3.1.7) under
    `/opt`, where nothing loads it, for the **vulnerability ceiling**;
  - `unsigned-build`: the production image under a local name, byte for byte, which the run did
    not pull and verify, for **build provenance**.
- **Caught while informing.** An informing check can never FAIL a run, so `harness mutants` counts
  such a mutant caught and attributed when its check reports a finding whose scope it did not
  report on the base in the self-test's own A/A. A finding production already has (no
  `HEALTHCHECK`, no SLSA provenance) never counts. The log says "caught by an informing check",
  and `mutants.json` and `scoreboard/mutants.jsonl` gain `planted` and `byInforming`.
- **build-provenance: unverified.** An image the run did not pull and verify (`local`,
  `built-from-ref`, `pulled-unverified`) can carry no verified SLSA provenance, so it is now the
  finding `<app>/unverified`, where it said "could not be evaluated". A `cached` image, verified
  when it was pulled, is still not evaluated.
- **a2 every night.** `main-preview.yml` passes `--a2` on every nightly run, and its dispatch input
  `a2` now defaults to on (about a minute and a half more per run). A night without a2 cannot be
  counted.
- **The clean-night count.** The readiness page gains a soak panel after the control chart (link
  "soak toward 2.0" in its header), and `readiness.json` gains `soak`. A night is clean when every
  nightly A/A of that night was clean and verified and that night's forecast found no difference
  between a and a2; a night on which main did not change pauses the count; anything else starts it
  again. Below the count, one row per policy check: its level, its quiet nights, its planted mutant
  and whether it may become blocking. `harness readiness` takes `--noise-history` (default: the
  copy `pages.yml` already puts in the site).

## What the first count will say

On the forecasts kept so far, two of the three checks fire on production as well as on main:
every app declares no `HEALTHCHECK`, and no image carries SLSA provenance (the monorepo's
`image-build.yml` publishes none). Neither can stay quiet until the monorepo changes production,
so the panel names them "fires every night on production too" rather than counting them down. The
vulnerability ceiling has held on every forecast. The 1 October A/A had one difference, so the
count starts from zero on 2 October.

## Upgrading

Nothing to do. A run decides exactly what it did before. The weekly mutants take about three more
release runs. A `harness mutants` run without a registry prefix (local images on both sides)
reports `unverified` on the base too, so `unsigned-build` has nothing new to show and escapes:
run it against pulled images, as `weekly-mutants.yml` does.
