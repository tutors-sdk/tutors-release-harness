# Harness 1.4.0 (contract 1.4.0)

Follow-ups to [1.3.0](1.3.0.md), which is merged. The harness version and the contract
version are both `1.4.0`; the contract changelog entry is in
[../contract.md](../contract.md#changes). Nothing in it is a break: a consumer written
against 1.3.0 keeps working. It is a **minor** release, not a patch, because it adds
environment variables with defaults, new commands and one new artifact, and because
reports say some things differently for the same two images (see
[Behaviour that changes](#behaviour-that-changes-without-a-flag-or-field)).

Per the contract's [versioning table](../contract.md#compatibility):

- **Minor:** new variables (`HARNESS_REQUIRE_ARTEFACTS`, `HARNESS_VULN_DB_MAX_AGE_DAYS`,
  `HARNESS_ROLLBACK_ISSUE`); new non-stable commands and their flags (`harness prune`,
  `harness vuln-db`, `harness local smoke`, `harness local compare`); the `mutant-noise-report` artifact; the
  canonical header forms, symmetric origins and redaction, which change hunks and hunk
  summaries; the one "NOT COLLECTED" text.
- **Patch-level** (bug fixes that make the code match the document): `harness --help`,
  `-h` and `help` work as documented; a claims or rules file that cannot be used is a
  clean message and exit `2`, not a stack trace; a run that cannot judge leaves no empty
  output directory; `post-deploy.yml` opens the rollback issue on exit `1` only; the
  post-deploy reason wording.

Nothing in it has been run against Docker, a registry or the real tools as a whole. The
unit tests drive every collector through an injected runner, and the grype parsers are
tested against real grype 0.119.0 output. What that cannot prove is listed under
[Pending validation](#pending-validation).

## What is new

- **A pinned vulnerability database.** `harness vuln-db update|status` fetches and reads
  one grype database in one directory (`HARNESS_VULN_DB_DIR`, else
  `<HARNESS_HOME>/vuln-db`); every scan runs with updates off against it, so both sides
  of a comparison see the same advisories. The nightly, the release job and the weekly
  mutants install grype at a pinned version, restore the database from a per-day cache
  and print its status first; `harness doctor` checks grype's version, the directory
  and the database's age (`HARNESS_VULN_DB_MAX_AGE_DAYS`, default 5, grype's own limit).
  [../images.md](../images.md#the-vulnerability-database).
- **One "NOT COLLECTED" convention**, see [below](#not-collected-one-convention).
- **Housekeeping commands.** `harness prune` frees `out/` and the image cache (a dry
  run unless `--yes`; never touches `HARNESS_HOME` state, the newest release run that
  did not FAIL, anything from the last six hours, or anything a running task holds),
  and `harness local smoke` (also `pnpm smoke`) is the two-stacks smoke that `ci.yml`
  now calls: both stacks boot, one journey runs A/A, the expanding migration passes and
  the contracting one is rejected. [../local.md](../local.md).
- **Main against the last release.** `harness local compare` (also `pnpm compare`) finds the
  newest release on quay.io (the highest `X.Y.Z` present for all four apps), pulls and
  verifies it and `main`, runs the gate's release step with no claims, and prints the verdict,
  the counts and where `report.html` is. An exploration: exit 0 whenever a report was
  produced, 2 when it could not judge, 1 for a harness fault; `--strict` follows the verdict
  like `local gate`. [../local.md](../local.md#compare-main-with-the-last-release).
- **Cleaner exit 2.** `--help`, `-h` and `help` print usage and exit 0; a claims or
  rules file that cannot be used is a multi-line message, not a stack trace; a run that
  cannot judge no longer leaves an empty output directory; `post-deploy.yml` opens the
  `rollback` issue on exit 1 only.
- **Post-deploy against an external side** (what a production run showed):
  `content-type` and `cache-control` are compared in one canonical form on both sides;
  header masks may carry a pattern (the CDN-only masks themselves land in a masks-only
  PR); production's own URLs read as `{{origin}}` on both sides; secret-shaped values
  (`apikey=`, `Authorization`, JWTs, `sb_publishable_`/`sb_secret_` keys) are redacted
  before a capture or a report holds them; a local WARN says `decide whether to roll back`
  and never promises an issue (`HARNESS_ROLLBACK_ISSUE`); `harness local watch` stamps its
  lines. Contract: [../contract.md](../contract.md#changes).
- **Workflows.** `release.yml` is titled `release <candidate>`, so a caller can find the
  run a dispatch started; `weekly-mutants.yml` uploads `mutant-noise-report` (7 days)
  when its self-test fails.

### Not collected: one convention

An artefact the harness cannot collect must never read as "no difference". Four
collectors said so in four ways:

| Artefact | Text | Hunk | Severity |
| --- | --- | --- | --- |
| `image-manifest`, `sbom`, `vulns` | `NOT COLLECTED: <kind> of <apps> on side b: <reason>. It was not compared.` (reasons); `<app>: sbom NOT COLLECTED on side b, so it was not compared` (hunk) | `<app>/not-collected` | informational, failing with `HARNESS_REQUIRE_STATIC=1` |
| `runtime`, `startup` | `<app>: container posture not collected: <reason> (side b)` | `<app>/not-collected`, `runtime/not-collected`, `startup/not-collected` | failing, informational when switched off |
| `bus` | `bus traffic not collected: no bus configured` | none | none: run log and `capture.json` only |

One helper, `src/not-collected.ts`:

- **Text**: `NOT COLLECTED: <what>[ of <subject>][ on side a|b, or on both sides]: <reason>`,
  the same in `reasons`, in a hunk `summary` and in the run log.
- **Hunk**: the artefact's own `artefact`, and `scope` `<subject>/not-collected`,
  where the subject is an app or, when the whole artefact is missing, the artefact
  (`runtime/not-collected`). These scopes are exactly what they were, so no existing
  claim (`artefact: runtime, scope: "*/not-collected"`) stops matching.
- **Severity, one rule**: informational, unless the artefact is *required*, and then
  failing; always informational when an operator switched it off (`--no-runtime`,
  `--startup-restarts 0`).
- **Required**: `runtime` and `startup` by default; anything named in the new
  `HARNESS_REQUIRE_ARTEFACTS=<list>` (artefact names, `static` for the three image
  artefacts, `all`). `HARNESS_REQUIRE_STATIC=1` stays as an alias for `static`; the two
  add up, an unknown name is an error (exit 2), and the list only ever adds, so no
  setting can loosen a gate. `harness doctor` and `harness vuln-db status` read the same
  requirement for grype.

Nothing changes in a verdict, an exit code, a hunk's `artefact`, `scope`, `path` or
`severity`, or a claim, on any run that does not set the new variable. Decided by the
owner for this release:

- **The convention ships with 1.4.0, with `runtime` and `startup` failing by default.**
  Both collectors run `docker`/`kubectl` against stacks the harness started itself, so an
  empty one is a fault (no such container, a probe that crashed), not a missing tool, and a
  nightly A/A whose ratchet is "0 artefacts not collected" (TESTING.md) would stop meaning
  anything if it went quiet. They are in the default required set (`DEFAULT_REQUIRED` in
  `src/not-collected.ts`).
- **`bus` stays informational and quiet until a bus exists.** It has the same text in its
  run-log line, and a `capture.json` `bus.reason` of `no bus configured` / `external
  deployment` (`capture.json` is not part of the contract), but adds **no hunk** by
  default, because [../bus.md](../bus.md) promises that a run with no bus is byte-for-byte
  what it was. With `HARNESS_REQUIRE_ARTEFACTS=bus` a side with no bus is a failing
  `bus/not-collected` hunk (never asked of a live deployment).
- **`HARNESS_REQUIRE_STATIC` stays as an alias** for `HARNESS_REQUIRE_ARTEFACTS=static`.

The **text** changed (a `summary`, a `reasons` line, the run log; the contract only
promises `artefact`, `scope`, `path` and `severity` of a hunk): a tool that matches a
summary must match the new form. The static artefacts' `reasons` line lost its trailing
"It was not compared."; the runtime and startup summaries say `on side b` inside the text
instead of a trailing `(side b)`. New: `HARNESS_REQUIRE_ARTEFACTS`, and per-artefact
requirement (`=sbom` fails only the SBOM gap, where `HARNESS_REQUIRE_STATIC=1` was all
three). The change is in `src/compare/**` and `src/not-collected.ts`, engine paths: this
release's version bump covers it.

## New flags, environment variables, report fields

| Kind | Since 1.4.0 |
| --- | --- |
| Stable commands and flags | none |
| Non-stable commands and flags | `harness prune`, `harness vuln-db update\|status`, `harness local smoke`, `harness local compare`, and the flags only `prune` takes (`--older-than-days`, `--keep-last`, `--image-cache-days`, `--yes`); `--only stacks|migration` for `local smoke`; `--strict` and `--no-load` for `local compare` |
| Environment | `HARNESS_REQUIRE_ARTEFACTS` (`HARNESS_REQUIRE_STATIC` is its alias for `static`), `HARNESS_VULN_DB_MAX_AGE_DAYS` (default 5), `HARNESS_ROLLBACK_ISSUE`; `HARNESS_VULN_DB_DIR`, unset, now means `<HARNESS_HOME>/vuln-db` once `harness vuln-db update` has made it |
| `report.json`, `noise-status.json`, dispatch payloads | none |
| `masks.yaml` | comments only (a header mask may now carry a `pattern`, see the contract; no mask was added) |
| Exit code | unchanged; `--help` is now `0` (it answered `2`), as the contract said |
| Artifacts | `mutant-noise-report` (`weekly-mutants.yml`, 7 days, only when the self-test failed) |
| Workflows | the nightly, the release and the weekly mutants install pinned grype and cache one vulnerability database (`HARNESS_REQUIRE_STATIC=1` in the first two); `ci.yml` calls `harness local smoke`; `release.yml` has a `run-name`; `post-deploy.yml` opens its issue on exit 1 only |

### Behaviour that changes without a flag or field

- A static image artefact that could not be collected is informational unless
  `HARNESS_REQUIRE_ARTEFACTS` names it (or `HARNESS_REQUIRE_STATIC=1`, which the nightly
  and the release job set). `runtime` and `startup` are as before.
- Canonical header forms, symmetric origins on an external side and redaction change
  what hunks say, and can remove hunks an earlier build showed; a report is comparable
  only with one of the same harness version. A consumer must not match a hunk's summary.
- The `NOT COLLECTED` text is one shape (above).
- `HARNESS_VULN_DB_DIR`, unset, means `<HARNESS_HOME>/vuln-db` when it exists; a machine
  that never ran `vuln-db update` behaves as before.
- Captures written before the redaction change keep an `apikey` value on disk in the run
  directory that recorded them; delete them, or the artifact, if that matters.

## Decisions taken

Recorded by the owner for this release:

- **Not collected: one convention**, shipping with `runtime` and `startup` failing by
  default and `bus` quiet (see above). `HARNESS_REQUIRE_STATIC` remains an alias.
- **The vulnerability database may be at most 5 days old** (`HARNESS_VULN_DB_MAX_AGE_DAYS`),
  grype's own default, so a doctor warning and a scan agree.
- **`HARNESS_REQUIRE_STATIC=1` in the nightly and the release job, not in the weekly
  mutants**: the nightly is the canary for a scanner or SBOM that silently stopped, a
  release must not pass without the SBOM and vulnerability diff, and the mutants judge the
  harness, not an image ([../images.md](../images.md#the-vulnerability-database)).
- **The post-deploy CDN masks are a masks-only PR**, after this one merges: what only exists
  because production sits behind Netlify needs the header-mask `pattern` mechanism that is
  in this release, and `masks.yaml` does not change here beyond comments.
- **1.4.0, not 1.3.1.** 1.3.0 merged with the local-first work; what followed adds
  variables with defaults and new commands, which the contract's versioning table makes a
  minor release. The harness and the contract move together.

## Pending validation

Nothing below could be done without Docker, a registry, network or the real tools. Each
must happen before the harness gates on the artefact concerned; the checklist of
[1.3.0](1.3.0.md#pending-validation) still stands for everything it lists.

- [ ] **grype in the workflows**: the workflows install it pinned and cache one database,
      but no run has yet: the first nightly must show `vuln-db status` usable, the `vulns`
      artefact collected on both sides, and the cache hit the next day.
- [ ] **`HARNESS_REQUIRE_STATIC=1` in the nightly and the release job**: the first nightly
      and the first release run must not fail on a `NOT COLLECTED` that a runner can fix
      (grype, syft, an SBOM attestation).
- [ ] **`harness local smoke` in `ci.yml`**: both stacks boot, the journey A/A is clean, the
      expanding migration passes and the contracting one is rejected, on a real runner.
- [ ] **`harness prune`** against a real `out/` and image cache on Windows and Linux
      (a dry run first).
- [ ] **A real post-deploy run against production** with the canonical headers, symmetric
      origins and redaction: the verdict should no longer be unreachable, and no `apikey`
      value may reach a report.
- [ ] **The `rollback` issue on exit 1 only**, and the run title `release <candidate>`
      found by the monorepo's `release-harness-report` workflow (a real dispatch).
- [ ] **`mutant-noise-report`** on a failed weekly self-test.
