# Harness 1.11.0 (contract 1.11.0)

The scoreboard (C2): one line per release run, kept for good, and the trends it makes visible.
1.9.0 gave every release a score and 1.10.0 filled its change-risk dimension; a score seen once
is a snapshot, and a line only tells you something once there are several points on it. 1.11.0
keeps them. Nothing in it is a break: a consumer written against 1.10.0 keeps working, and no
verdict or exit code changes. It is a **minor** release because it adds a command, a guard, five
flags and two files. The contract changelog entry is in [../contract.md](../contract.md#changes);
the Lean view behind it is [docs/lean.md](../lean.md).

## What is new

- **`scoreboard/releases.jsonl`** ([schema](../contract/scoreboard-line.schema.json), not
  stable): one JSON line per release run with the tag, run number, date, gate, RCS and band, the
  eight dimensions, masks applied and never fired, claims and stale claims, journeys passed, the
  latest mutants self-test, and the per-PR risk lines of `changes.json`. Append-only.
- **`harness scoreboard append --run <dir | confidence.json>`** builds that line from what a
  `harness release` run left behind and appends it. **`harness release` does this itself** after
  the score, into `HARNESS_HOME/scoreboard/releases.jsonl` (`--scoreboard <file>` for another), and
  prints the line and any run rule firing right after the RCS.
- **`harness scoreboard trends [--json] [--site dir]`** reads the file into six views: the RCS
  over releases with its bands; each of the eight dimensions over releases; masks (count and never
  fired); claims (and stale); hotspots (the files touched by the most releases, refactor
  candidates at three or more); risk per file and per contributor. `--site` writes
  `scoreboard.html` (inline SVG, the Green, Amber and Red bands shaded, no script) and
  `scoreboard.json`; the Pages site publishes both.
- **The harness's own health** on the same page: mutants caught per week (a new `mutants.json`
  from `harness mutants`, recorded by `harness scoreboard mutants`), noise-run cleanliness over
  the last 30 nights, and days since the last A/A failure.
- **`harness guard scoreboard`**: a diff may only add lines to `scoreboard/*.jsonl`. `guard all`
  runs it; CI's masks job runs it on every pull request.

## The run rules

Statistical process control, over the RCS and each of the eight dimensions, from
`src/scoreboard/trends.ts`:

| Rule | Fires at a release when | Opens |
| --- | --- | --- |
| `three-declines` | the series fell three releases running (four points, each lower than the last) | a kaizen item naming the series and the four values |
| `two-of-three-below-75` | two of the last three releases are strictly below 75, the Amber line | a kaizen item naming the series and the three values |
| open countermeasures only rising | the kaizen register's open count rose and never fell | not measured yet: `kaizen/README.md` comes with C4 (`harness why`), and the trends say so |

A release where the series was not measured is skipped, never counted as 0 or 100. Each firing
says whether its window spans a change of `weightsVersion` (a new hash of the weights, floors,
bands and rules, now in `confidence.json`): a fall caused by rescoring is a discontinuity, not a
decline, and the trends and the page say so. **Advisory: a run rule opens an item for people to look at. It
never feeds the Gate and never changes a verdict or an exit code.**

## An honest empty state

There is no seed data. The file ships empty and the page says "No releases scored yet." until a
real release run adds a line; every view and the run rules say the same. A made-up history would
draw a trend nobody lived through.

## How a line gets there

`main` takes changes only through pull requests, so CI never commits to it. Instead:

- `release.yml`'s new `scoreboard` job (after the release, migration and upgrade runs, pass or
  fail) scores the three reports with `harness confidence`, measures change risk with `harness
  changes` against the monorepo, appends the line, and pushes it to the **`scoreboard` branch**
  of this repository, one commit per line.
- `weekly-mutants.yml`'s new `record` job appends the week's self-test to
  `scoreboard/mutants.jsonl` on the same branch.
- Both share one concurrency group, never force-push, and check before pushing that the old file
  is exactly the start of the new one.
- `pages.yml` reads the branch and publishes `scoreboard.html` and `scoreboard.json`.
- To bring lines onto `main`, open a pull request that copies them; the guard lets it only add.

A re-run of a tag is a new line with the next run number: the trends plot the latest run and list
the earlier ones as deviations. A `--fast` run is never appended (it cannot support a go
decision); a failing run is, with its RCS as null, because a failure is part of the history.

## Guardrails, in code

- **The Gate wins.** The scoreboard stage of `harness release` runs after the verdict; if it
  cannot append, it says so in one line and nothing else changes. Tests hold that the exit code
  is the same with a board, without one, and when appending fails.
- **Append-only, three times over**: `harness scoreboard append` only ever appends, the CI jobs
  check the file only grew, and `harness guard scoreboard` fails a pull request that edits,
  reorders or removes a line.
- **Contributor lines are for trends, never people's reviews.** The per-contributor view is
  labelled so on the page and in the JSON.
- **Not measured is not a value.** A dimension without data is a gap in its line, not a drop to 0.

## Behaviour that changes without a flag or field

- `harness release` prints a scoreboard line after "confidence:", and `report.md` and
  `report.html` have a "Scoreboard" section. Its plan (`--dry-run`) names the file it will append
  to. Exit codes are unchanged.
- `harness guard all` runs three guards (masks, engine, scoreboard) where it ran two.
- CI's masks job runs `harness guard scoreboard`.
- `harness mutants` writes `mutants.json` into its `--out`, and `weekly-mutants.yml` uploads it as
  `mutants-summary`.
- `confidence.json` carries `weightsVersion`.
