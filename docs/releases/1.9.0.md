# Harness 1.9.0 (contract 1.9.0)

The Release Confidence Score (C0): after the Gate, one percentage that says how much the
evidence behind a pass is worth, broken into eight dimensions so the whole team reads it the
same way. Nothing in it is a break: a consumer written against 1.8.0 keeps working, and no
verdict or exit code changes. It is a **minor** release because it adds a command, seven flags
and an output file. The contract changelog entry is in [../contract.md](../contract.md#changes);
the Lean view behind it is [docs/lean.md](../lean.md).

## What is new

- **`harness confidence --run <release run | harness release dir>`** writes `confidence.json`
  beside what it scored and prints the board: the Gate first, then the RCS and its band with
  what the band means, then the eight dimensions, each with every point lost and where. See
  [../local.md](../local.md#the-release-confidence-score-harness-confidence).
- **`harness release` scores every run.** Its score stage, a seam in 1.8.0, now writes
  `confidence.json` into `out/<timestamp>-release-command/`, and `report.md`, `gate.md` and
  `report.html` lead with the Gate, then `RCS <n> <band>: <meaning>`, then the dimension table.
- **`confidence.json`** ([schema](../contract/confidence.schema.json), not stable): `gate`,
  `rcs`, `band`, `meaning`, `mean`, `weightsUsed`, the eight `dimensions` with their
  `deductions` (`points`, `why`, `evidence`), `glance` (empty until C3) and `run`.
- **`report.html` of a run has anchors** (`#hunk-<id>`, `#stale-claims`, `#masks`, `#noise`,
  `#load`, `#migration`, `#upgrade`, …), so each deduction links to the exact row it is about.

## How the number is made

| Dimension | Weight | Floor (caps the RCS at 74) |
| --- | --- | --- |
| Claim coverage | 20 | any broad claim, or more than 2 stale claims |
| Noise health | 15 | no usable A/A (none, `--noise skip`, dirty or degraded), or one older than 7 days |
| Statistical margin | 10 | a p-value in 0.05-0.10, or a k6 failure rate above 0 |
| Rehearsals | 10 | either rehearsal skipped |
| Test signal | 15 | a mutation score below 60%, or a harness mutant missed |
| Requirements traceability | 10 | a new-feature changelog entry with no EARS file |
| Change risk | 15 | a PR merged without review |
| Post-deploy history | 5 | the last release's post-deploy check FAILED |

Each dimension is 100 minus its deductions. The RCS is the weighted mean of the measured
dimensions, rounded down, capped at 74 when any floor is breached. Bands are fixed: **Green**
≥ 90, ship on the captain's say; **Amber** 75-89, ship only after the reviewer's glance is
recorded verified; **Red** < 75, hold, open a 5 Whys, do not re-run hoping for a better number.
Every deduction and its points are in [../contract.md](../contract.md#confidencejson-the-release-confidence-score).

## A worked example: 16.3.0-rc.1 (fictitious)

The release run passes the Gate. What it and the inputs say:

| Dimension | What was found | Deduction | Score |
| --- | --- | --- | --- |
| Claim coverage | one stale claim, `dom reader:old` (Rule 0040), matched nothing | −15, `report.html#stale-claims` | 85 |
| Noise health | the A/A is clean, verified and hours old; two masks fired nothing | −5 each, `report.html#masks` | 90 |
| Statistical margin | no timing p-value at or below 0.20; k6 failed nothing | none | 100 |
| Rehearsals | migration and upgrade both pass, no failed request | none | 100 |
| Test signal | mutation score 72% on reader (`--test-signal`) | −30, below 80% | 70 |
| Requirements traceability | every entry has an EARS file and a claim (`--traceability`) | none | 100 |
| Change risk | PR #412, a first contribution, touches a hotspot file (`--change-risk`) | −40, PR #412 | 60 |
| Post-deploy history | 16.2.2's post-deploy check passed (`--post-deploy`) | none | 100 |

Weighted mean: (20×85 + 15×90 + 10×100 + 10×100 + 15×70 + 10×100 + 15×60 + 5×100) / 100 =
8500 / 100 = **85.00**. No floor is breached, so **RCS 85, Amber**: the glance is mandatory,
and it points at the hotspot change and the stale claim first. (The companion plan's text gives
this example as 84.5 and RCS 84; with its own weights the sum is 85.00. Same band, same glance.
`tests/confidence.test.ts` builds the example from these inputs, not from the eight numbers.)

The same candidate with the upgrade rehearsal skipped: rehearsals 50, a breached floor, and a
mean of 80.00 is capped to **RCS 74, Red**: hold, whatever the other seven say.

## Honesty rules, in code

- **The Gate wins.** A FAIL, an overridden FAIL or NOT JUDGED gets `rcs: null` and `band:
  null`; the dimensions are still there, for the 5 Whys. `harness release` decides its exit
  code before the score is computed; `src/gate.ts` and `src/run.ts` import nothing under
  `src/score` (a test follows their imports to be sure).
- **Deductions are explainable or they are removed.** Every point lost names a hunk, a claim,
  a PR, a file or a run, with a link.
- **Not measured is not 100.** On a real `harness release` run today, claim coverage, noise
  health, statistical margin and rehearsals are measured from its own runs. Test signal,
  traceability and post-deploy history need the monorepo's data (`--test-signal`,
  `--traceability`, `--post-deploy`), and change risk needs C1 (`--change-risk`). Without their
  input each is `not measured`, with the reason; the mean is taken over the rest and
  `weightsUsed` records the renormalised weights.
- **Weights and bands are constants in one file**, `src/score/weights.ts`, and change only by a
  PR with a 5 Whys attached, never in the release that would benefit.
- **Advisory for now.** Three real releases show whether the weights match the team's
  judgement before a band holds anything.

## Behaviour that changes without a flag or field

- `harness release`'s score stage is `done` (or `skipped` with a reason: no release run to
  score, or an input it could not read) instead of always `skipped`, and its terminal output
  gains one line, `confidence: …`, after the gate line. Exit codes are unchanged.
- Run `report.html` files gain `id` attributes; nothing visible changes.
