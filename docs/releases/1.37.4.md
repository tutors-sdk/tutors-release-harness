# Harness 1.37.4 (contract 1.37.0)

A page capture no longer waits on fire-and-forget requests. A harness-only **patch**: no input, output field,
claims key, flag, workflow or mask changes, so the contract stays at 1.37.0.

## Why

Main to RC has reported "journey student-signs-in slower on b", about 23 s against 4 s. With the same images on
both sides (a diagnostic run on 15 Oct 2026), main's reader took 23 s on either side and 17.0.0 took 4 s, so the
slowdown followed the image. A trace showed the course page rendering in under a second on both, and one request
still open on every signed-in page: `POST /api/live/activity`, the reader's learning event (mono-repo #481). The
reader sends it as a `keepalive` fetch; the server answers 202 at once, but headless Chromium never reports a
keepalive request finished. Before each capture the harness waited for Playwright's networkidle (5 s timeout) and
then for its own in-flight count to reach 0 (5 s at most), so each signed-in page cost 10 s of waiting that no
student sees.

## What changed

- `captureJourney` keeps the requests in flight as a set and settles a request that is not a read (anything but
  GET and HEAD) once its response status arrives. Reads still wait for their body, so a capture never takes an
  image or stylesheet half loaded.
- The wait before each capture is the harness's own count alone (`quiet`, 500 ms of nothing in flight, 5 s at
  most). Playwright's networkidle is no longer awaited there: it waits on the same keepalive requests.
- `settlesOnResponse(method)` is exported for its test (`tests/collectors.test.ts`).

Timing comparisons between a release before #481 and one after it read the same again; a run judged by 1.37.3 and
one by 1.37.4 are not comparable on student-signs-in.
