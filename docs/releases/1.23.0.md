# Harness 1.23.0 (contract 1.23.0)

OpenVEX: exceptions the scanner reads. Until now the only way to say "this advisory does not apply
to us" was a claim, which the harness alone understands and which says "we accept this change", not
"this is not a vulnerability here". The monorepo can now keep `release/openvex.json` beside
`release/claims.yaml`, an [OpenVEX](https://openvex.dev) document any scanner reads, and the harness
hands it to the grype it already pins. The third step of the "Policy" release. The contract
changelog entry is in [../contract.md](../contract.md#changes). A **minor** for one new stable
flag.

## What is new

- **`harness run --vex <file>`** hands the file to the scanner on both sides (`grype ... --vex`,
  and trivy, which takes the same flag). An advisory the scanner sets aside under a statement is
  left out of `vulns` and of the vulnerability ceiling, on a and b alike, so no diff moves because
  of it.
- **Checked before anything starts.** A file the harness cannot use is exit `2`, naming the
  statement and the field. `not_affected` needs one of the five standard justifications; an
  `impact_statement` alone is not enough. `affected` needs an `action_statement`. A product is a
  package URL (`pkg:npm/tar@7.4.3`), because the harness scans SBOMs and grype matches a statement
  by the vulnerable package's purl.
- **Visible.** The scan records the file (name, sha256, statement counts) and the advisories it set
  aside; the report's image artefacts line for `vulns` says "OpenVEX openvex.json (N
  statement(s)): M set aside, ids".
- **Wired in.** `release.yml` fetches `openvex.json` beside `claims_url`, Main to RC beside main's
  claims; `harness local gate` takes `--vex`, and `harness release` reads `release/openvex.json` in
  the monorepo checkout when `--vex` is omitted.

## What it changes today

Nothing, until the monorepo keeps a file. With none beside the claims (a 404), every run is the run
it was. The monorepo's first `release/openvex.json` has no statements and its own check,
`pnpm check:openvex`, holds the same rules; a statement for the `tar` advisory belongs there only
once the evidence says the vulnerable code cannot be reached.

## Upgrading

Nothing to do. To use it, add `release/openvex.json` beside `release/claims.yaml`.
