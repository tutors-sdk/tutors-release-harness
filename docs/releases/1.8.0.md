# Harness 1.8.0 (contract 1.8.0)

One command from a pushed candidate to a report: `harness release`. Nothing in it is a
break: a consumer written against 1.7.0 keeps working. It is a **minor** release because it
adds a command, five flags, an environment variable and an output directory. The contract
changelog entry is in [../contract.md](../contract.md#changes).

## What is new

- **`harness release --candidate <tag>`**. The release gate's plan (the steps `harness local
  gate` and `release.yml` run) as seven stages: resolve, noise, changes, release, rehearse,
  score, report. It asks nothing, retries nothing silently, and always leaves `report.md` and
  `report.html` behind in `out/<timestamp>-release-command/`, a stopped line or Ctrl-C
  included. Each stage prints one line with its elapsed time. See
  [../local.md](../local.md#one-command-for-a-release-harness-release).
- **The baseline is what production runs.** `--baseline <tag>`, or `prod` (the default)
  reads `release/deployed.json` in the monorepo checkout (`--monorepo`, or
  `HARNESS_MONOREPO_DIR`); its `digests` pin production. Without one it falls back to
  `HARNESS_PRODUCTION_TAG`, and with neither it stops with exit 2 before anything runs. The
  monorepo writes `deployed.json` in a later PR of its own.
- **The A/A comes first.** The local noise store's status is reused when it is clean,
  verified and at most 7 days old; otherwise the command runs an A/A of the baseline (3 runs)
  before any A/B. A dirty one stops there and names each difference that needs a mask
  reviewed or a determinism fix.
- **`status.json`** is rewritten at every change with the stage running and each stage's
  state, start, elapsed and expected seconds, so a dashboard can show "running: release, 14 of
  25 min" ([schema](../contract/release-status.schema.json), not stable).
- **`--fast`**: one run, no load, no rehearsals and no A/A of its own, for a branch. The
  terminal, `report.md`, `report.html` and `status.json` all say it cannot be used for a go
  decision.
- **`--open`** opens `report.html` with the platform's opener; **`--dry-run`** prints the
  baseline, the noise decision and every command.

## Lean in the harness

| Idea | In 1.8.0 | Still to come |
| --- | --- | --- |
| Jidoka (stop the line) | missing images, a dirty A/A and a gate FAIL each stop the line; the terminal and the report say `line stopped at <stage>: <why>` and the next standard step | the 5 Whys each stop opens (C4) |
| Andon (visual management) | the report opens with the gate in one word (PASS, WARN, FAIL, NOT JUDGED); `status.json` is the board | the score and its band (C0), the scoreboard (C2) |
| Standard work | the same stages, the same steps as CI, a named next step for every stop | the SOP in the monorepo (C3) |
| Gemba | each gate row links to that run's own report | the glance: at most seven ranked places to look (C3) |
| Kaizen | a FAIL is marked as a 5 Whys trigger in the report | `harness why` and the countermeasure register (C4) |

The changes and score stages are seams that say "not built yet" and make nothing up. Whatever
they later return, the gate wins: they can never change a verdict or an exit code.

## Behaviour that changes without a flag or field

- None for existing commands. `pnpm release` is still `harness run --mode release`; the one
  command is `pnpm harness release`.
- Posting `report.md` to a pull request is not built: with `GITHUB_TOKEN` set the command says
  where the file is and posts nothing.
