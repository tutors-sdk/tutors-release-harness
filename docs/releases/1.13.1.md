# Harness 1.13.1 (contract 1.13.1)

The exemplar. The report pages at
[tutors-sdk.github.io/tutors-release-harness](https://tutors-sdk.github.io/tutors-release-harness/)
now open with **What main would ship today**: the newest Main to RC forecast, main judged as if it
were cut as a release candidate now, against the release in production. It is the report every
release gets, shown on the one change that is always there to show. Before this release the
forecast was release mode only, so the page could show a verdict and a scorecard, but not the
Release Confidence Score, its band, the reviewer's glance or the change risk that 1.9.0 to 1.13.0
added. Nothing here changes a verdict or an exit code. No command or flag is added. The
contract changelog entry is in [../contract.md](../contract.md#changes). The Lean view behind the
report is [docs/lean.md](../lean.md). How to run a release yourself is
[docs/user-guide/10-running-a-release.md](../user-guide/10-running-a-release.md).

## What is new

- **Main to RC is scored the way a candidate is scored.** `main-preview.yml` has two new jobs,
  `migration` and `upgrade`. They rehearse main the way `release.yml` rehearses a candidate. The
  `publish` job then runs `harness changes`, which reads the monorepo's history from production's
  `v<tag>` to the commit that was judged and writes `changes.json`. After that it runs
  `harness confidence` over the release run, both rehearsals and `changes.json`. That writes
  `confidence.json`: the Gate, the RCS and its band, the eight dimensions and the glance. The
  glance's novelty is read from the `scoreboard` branch. All of this happens after every verdict,
  and nothing here can reach one. A FAIL in a rehearsal is still a forecast. A step that cannot run
  says why, and the forecast is kept without it. Nothing is appended to the scoreboard, because a
  forecast is not a release.
- **The kept report has the same lead as `harness release`.** When `harness reports keep` keeps a
  release run that has its score beside it, it also keeps `confidence.json` and `changes.json`. It
  leads `report.md` and `report.html` with the Gate, then the RCS and its band, then the glance,
  the dimension table and the change risk per PR. The run's own report follows unchanged. One
  renderer serves both: `src/report/lead.ts`, which `harness release` now uses too. The run's
  entry in `reports/index.json` gains `confidence` (`gate`, `rcs`, `band`, `meaning`, `note`,
  `glance`, `scoredBy`) and `changes` (`score`, `prs`, `risky`, `floorBreached`, `range`).
- **The page leads with it.** At the top of `site/index.html`:
  - the Gate;
  - the RCS and its band, with the band's one-line meaning (for a FAIL there is no number, only
    the score's own reason why not);
  - what stops the line;
  - where to look first: the glance, each item linked to its hunk in the kept report and to its
    PR;
  - what changed: the change risk and the PRs that lost points;
  - when it ran and which harness ran it;
  - links to the full report, the run, docs/lean.md and the how-to-run guide.

  Below it, as before, come the scoreboard, the release candidates, every forecast and the
  nightly A/A.
- **Honest about older forecasts.** A forecast kept before the score existed (the one on the
  branch today was kept by 1.4.11) is shown as it was scored. The page says: "scored by harness
  1.4.11 before the confidence score existed", and that the next forecast will carry the score.
  It shows no number, band or glance it does not have.

## What you will see

The first forecast judged by 1.13.1 replaces the old one at the top of the page. Because a new
harness version judges the same pair again, that is the next morning's run after this reaches
main, or sooner with `workflow_dispatch` and `force`. Until then the top shows the 1.4.11 forecast
and says it was scored before the confidence score existed.

## Upgrading

Nothing to do. A reader of `reports/index.json` that ignores unknown fields keeps working. An
entry without `confidence` or `changes` was not scored, and a reader must not assume anything
about it. No new permission: `publish` still holds `contents: write` and pushes only
`main-preview`. The two new artifacts, `main-preview-migration-report` and
`main-preview-upgrade-report`, are kept for 14 days.
