# Harness 1.53.0 (contract 1.53.0)

A threshold on first-load JavaScript. A **minor**. Part of the harness hardening plan (production-readiness additions, tranche 1, item E4).

## Why

`asset-graph` already counted the immutable JS and CSS each app asks for and their bytes, and said so, but with no threshold: a release that doubled what a student downloads on first load read the same as one that renamed a chunk.

## What changed

- `src/compare/asset-graph.ts`: `<app>/first-load-js`, when a page b loads as a document (run 1, a page both sides reached) asks for at least **10% and 50 KB** more JavaScript under `/_app/immutable/` than a's same page did, by the responses' own `content-length`. The same shape as the image-size rule (10% and 5 MB). The hunk names the page that grew most, with a → b and the percentage.
- Left out, never guessed: a client-side route change (no document load), and a page where any JS response did not say its size. Shrinking is never a finding.
- `mutants/wrap.mjs`: `extra-chunk`'s planted chunk weighs 1 MiB (a comment), so the threshold has a planted change it must catch, not only the request count.

## Not done

The plan said to read the monorepo's `tests/performance/bundle-budgets.json` when present. Its ceilings are gzip totals of a whole build (all chunks, every route), which no page's first load is, and the monorepo's own PR check (`pnpm check:bundle`) already gates on them; comparing a page's transfer to a build total would be a number that means nothing.

## Level

Informing, like the rest of asset-graph: reported, claimable, never gates. It becomes blocking with asset-graph at 2.0. No verdict, Gate, score or exit code moves.
