# Harness 1.61.0 (contract 1.61.0)

The nightly A/A and Main to RC judge what production actually serves, not only what the pin says. This is a **minor**: a new command, `harness production resolve`, and the flag `--pinned`.

## Why

On 3 November 2026 tutors.dev (Netlify, deployed by hand) was moved to `b146cca`, the 17.1.0 release-prep merge, tagged `v17.1.0-rc.1`. No final `v17.1.0` was tagged, so no `pnpm deploy:pin` pull request was opened, `release/deployed.json` and the overlays stayed at 17.0.0, and `deploy.yml` never set `HARNESS_PRODUCTION_TAG`. That night's A/A (run 41754390229) measured 17.0.0 and Main to RC would have judged main against 17.0.0. Post-deploy had seen it from 17:01 ("production build: differs ... build name 0a42da52a0e1e453", the hash of `b146cca`), but only for information.

## What changed

- `src/ci/live-production.ts`, `harness production resolve`: asks production's reader (`/version` revision, else the `/_app/version.json` build name), matches the commit to the monorepo's release tags (final before rc) and then to main's newest 100 commits (`sha-<short>`), and falls back to `--pinned`. A disagreement with the pin is a `::warning` and a summary line.
- `nightly-noise.yml`: a `production` job resolves the tag before the A/A; `HARNESS_PRODUCTION_TAG` is the fallback, and a dispatched `tag` is used as given.
- `harness preview resolve` (Main to RC): side a is the tag production serves, the overlay's `newTag` the fallback; drift is warned, and the stale-pin warning stays for when production comes from the overlay.
- `src/modes/production-build.ts`: `askProduction` (the reader's answers, unjudged) and `sameCommit` exported for the above.

## Expect

Tonight's A/A measures `17.1.0-rc.1` with a warning "production serves 17.1.0-rc.1 (commit b146cca3900e), but the pin says 17.0.0", Once `v17.1.0` is tagged on that commit the tag becomes `17.1.0` (a final tag wins over its rc), and the warning goes when that release's pin pull request merges.
