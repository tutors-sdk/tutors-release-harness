# Harness 1.10.0 (contract 1.10.0)

Change signals (C1): what changed between the two tags the diff engine compared, one risk line
per pull request, and the change risk they add up to. It fills the changes stage of `harness
release` and the Release Confidence Score's change-risk dimension, which 1.9.0 left "not
measured". Nothing in it is a break: a consumer written against 1.9.0 keeps working, and no
verdict or exit code changes. It is a **minor** release because it adds a command, two flags
and an output file. The contract changelog entry is in [../contract.md](../contract.md#changes);
the Lean view behind it is [docs/lean.md](../lean.md).

## What is new

- **`harness changes --a <tag> --b <tag> [--monorepo dir] [--history 6] [--changelog f]
  [--json] [--out file]`** reads `git log A..B` in the monorepo checkout and prints the board:
  the change risk, one line per PR (risky first), where every point went, the release-level
  signals, and what could not be measured. See
  [../local.md](../local.md#what-changed-pr-by-pr-harness-changes).
- **`changes.json`** ([schema](../contract/changes.schema.json), not stable): the per-PR lines
  (`pr`, `title`, `files`, `churn`, `hotspotsTouched`, `testDelta`, `reviewed`,
  `firstContribution`, `deductions`), the signals, `notMeasured`, and the `changeRisk` block
  the score reads.
- **`harness release` measures change risk.** With a monorepo checkout (`--monorepo` or
  `HARNESS_MONOREPO_DIR`, the same one that names the baseline) its changes stage runs
  `harness changes --a <baseline> --b <candidate>`, writes `changes.json` beside
  `confidence.json`, and the score stage reads it. `report.md`, `gate.md` and `report.html` show
  the per-PR table right under the dimension table. No checkout: the stage is skipped with the
  reason and change risk stays not measured.
- **`harness confidence --change-risk`** takes a `changes.json`. The 1.9.0 `{ "prs": [...] }`
  shape is still read.

## The signals and what they cost

The plan's table ("Code-level change signals"), in `src/score/weights.ts` beside the weights,
applied per PR in `src/changes/signals.ts`:

| Signal | Measured as | Costs |
| --- | --- | --- |
| Churn | lines added + deleted under `apps/reader`, `apps/catalogue`, `apps/live`, `apps/time`, against that app's median over the last 6 releases (plain `vX.Y.Z` tags; an rc is not a release) | −5 per app above 2×, on the PR with most of it |
| Hotspots | production files changed in 3+ of those 6 releases, heaviest first | −10 when a first contribution touches one, −3 otherwise |
| Ownership dispersion | production files with 3+ authors this release | −5 each, at most −15, on the PR that brought the third |
| Orphan changes | a diff under a product section no `### v<version>` entry names; an entry whose PRs did not merge or changed nothing under its section | −10 each, and a floor signal for requirements traceability |
| Test delta | test lines ÷ production lines per package (root `tests/` count for the PR's own packages) | −10 per PR below 0.2 |
| Review coverage | at least one approving review, from GitHub's REST API | a floor breach (caps the RCS at 74), no points, per PR without one and per commit straight to main |
| Dependency movement | direct dependencies in `pnpm-lock.yaml`, baseline against candidate | −5 per major bump; new ones listed |

Change risk = 100 − the **sum** of every PR's deductions, floored at 0. A sum, not an average:
six small clean PRs cannot dilute one risky one, and the report's table shows exactly that,
one row for the risky PR and one folded row for the six.

## The real 16.2.1 → 16.2.2

`harness changes --a 16.2.1 --b 16.2.2 --monorepo tutors-mono-repo`, with a token:

| PR | What it did | Found | Points |
| --- | --- | --- | --- |
| #259 | restore accents and umlauts in four message files | a first contribution (a fact); 358 production lines in `packages/svelte/utils`, no test lines; no approving review | −10, floor |
| #262 | rewrite the testing guides, fix two nightly jobs | no approving review | floor |
| #257 | settle the page before the axe audit | no approving review | floor |
| #263 | convert Lo summaries when the course tree is built (95 test lines for 30 production lines) | no approving review | floor |
| #264 | the release branch (version bump, changelog) | no approving review | floor |

**Change risk 90, floor breached.** Churn was small in every app (2 lines each, the version
bump, against medians of 3.5 to 105.5), no hotspot was touched, no file had three authors, no
orphan (every PR is in CHANGELOG.md, every entry has its diff), no major bump. What the number
says plainly is that nothing in 16.2.2 merged with an approving review: that caps the RCS at 74
until the practice changes, which is what the floor is for. Without a token the same run reports
review coverage as not measured and change risk 90 with no floor: it does not guess.

## Guardrails, in code

- **The Gate wins.** `harness changes` is advisory: exit `0` whatever it found. In `harness
  release` its exit code is not added to the gate's results and it is not a step of `gate.json`;
  tests hold that the command's exit code is the same with it, without it, and when it fails.
- **Every deduction is explainable.** Each names its PR (or commit) and file, with a link to
  that file in that PR's diff; `rule`, `pr`, `file` are fields, so the scoreboard can follow a
  file or a PR across releases.
- **Contributor lines are for trends and glances, never people's reviews.** The author is a
  fact field in `changes.json`, never part of a reason, never a column in the report. A first
  contribution costs nothing on its own; the points land only when it meets a hotspot (−10
  instead of −3) or lacks tests (the −10 anyone's PR would lose). Tests hold both.
- **Not measured is not clean.** No token, no GitHub remote, no changelog for the version, no
  history, no lock file: the signal is listed as not measured, with the reason, costs nothing,
  and is a gap of the change-risk dimension. A commit straight to main breaches the review floor
  either way: that is known from git alone.
- **Orphans are reported, never fatal.**

## Behaviour that changes without a flag or field

- `harness release`'s changes stage is `done` (with a checkout) or `skipped` with the reason,
  where 1.9.0 always said "not built yet (C1)". Exit codes are unchanged.
- Change risk's points follow the plan's table: a hotspot touched by a first contribution is
  −10 (1.9.0: −40) and by anyone else −3 (1.9.0: nothing); a PR with no approving review breaches
  the floor at no points (1.9.0: −40 and the floor). The plan's worked example (16.3.0-rc.1)
  therefore scores change risk 90 and RCS 89, still Amber.
- A deduction in `confidence.json` may be `points: 0` with `floor: true`, shown as `floor`.
