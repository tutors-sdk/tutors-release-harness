# Harness 1.36.3 (contract 1.36.0)

Migration rehearsal starts from production's legacy tables. A harness-only **patch**: no input,
output field, verdict, exit code, claims key, flag, workflow or mask changes, so the contract stays
at 1.36.0.

## Why

Tutors' Supabase schema predates `supabase/migrations`: production has `tutors-connect-latest`,
`calendar`, `learning_records`, `tutors-connect-users` and `tutors-connect-courses`, but no migration
creates them. 17.0.0 is the first release whose migrations touch them (an index on
`tutors-connect-latest`, `record_page_view`/`record_heartbeat` writing `learning_records` and
`calendar`, an index on `calendar`). The rehearsal's throwaway Postgres had only the platform
baseline, so Main to RC and the 17.0.0-rc.1 gate failed with
`relation "public.tutors-connect-latest" does not exist`: a gap in the harness, not in the release.

## What changed

- `fixtures/migrations/supabase-legacy-tables.sql` creates those five tables with the shapes in the
  monorepo's `packages/jsr/types/src/rows.ts` and the unique keys its upserts name. Migration mode
  applies it after `supabase-baseline.sql` and before version a's migrations. With `--snapshot` it is
  skipped, because the snapshot carries the real tables.
- Tables with no row type in the monorepo (`tutors-connect-profiles`, `assignments`,
  `assignments_submissions`, ...) are left out until a migration needs them.

Checked by applying the baseline, the fixture and every migration on monorepo main to Postgres 16,
then calling `record_page_view` twice and `record_heartbeat` once (counts 2, durations 3).
