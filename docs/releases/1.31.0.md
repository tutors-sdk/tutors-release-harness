# Harness 1.31.0 (contract 1.31.0)

Real courses on the A3. The contract changelog entry is in [../contract.md](../contract.md#changes). A
**minor**, for a new `a3.json` field and a workflow change. **The verdict never moves**: the Gate, the
score and every exit code read nothing new.

## Why

1.30.0 shows a captured course loads in one reader. A release decision needs the same question asked of
both sides: does every real course a student uses still load on main, as it does on production? The
fixture course is two topics; the corpus is what students actually read.

## What is new

- **`course-capture.yml`, job `corpus`**: production on side a and main on side b, resolved as Main to
  RC resolves them (`harness preview resolve --force`). The corpus is checked in both readers, and the
  `course-corpus-check` artifact keeps `sides.json`, `a/<course>/course-check.json` and
  `b/<course>/course-check.json`. Nightly at 04:47 UTC as well as weekly and on demand.
- **`pages.yml`** rebuilds after `Course capture` and copies the newest corpus check of a run on `main`
  into the site's `courses/`.
- **The A3: Real courses** (`courses` in `a3.json`). Under the current condition, a table per course:
  production and main, pages loaded, the first pages that did not load, the median time to the title on
  each side and the difference, and the state (loads on both, breaks on main, fixed on main, fails on
  both). A fact line, and a goal row "Real courses load on main (course corpus)". A course that loads on
  production and breaks on main is named in the fact line: a student on it would be stopped by the
  release.

One check per side is a reading, not a benchmark: the times sit beside each other and are never judged.

## Next

and up to four module courses in the corpus beside the standard.
