# Harness 1.5.0 (contract 1.5.0)

Follow-ups to [1.4.0](1.4.0.md). Everything below was already on `main`, shipped one pull
request at a time as harness patches 1.4.1 to 1.4.14 while the contract changelog carried it
as "1.5.0 (unreleased)". This release names it: the harness version and the contract version
are both `1.5.0`; the contract changelog entry is in [../contract.md](../contract.md#changes).
Nothing in it is a break: a consumer written against 1.4.0 keeps working. It is a **minor**
release, not a patch, because it adds non-stable commands, a flag, an environment variable
with a default, an artifact, two workflows and one new write scope, and because reports say
some things differently for the same two images (see
[Behaviour that changes](#behaviour-that-changes-without-a-flag-or-field)).

Per the contract's [versioning table](../contract.md#compatibility):

- **Minor:** new non-stable commands (`harness reports keep`, `harness scorecard`,
  `harness preview resolve`) and the `--force` flag; `HARNESS_THIRD_PARTY_CACHE_DIR`
  (default `<HARNESS_HOME>/third-party-cache`); the `main-preview-report` artifact; the
  `main-preview.yml` and `pages.yml` workflows; kept reports on the `noise`,
  `release-records` and new `main-preview` branches; the changes in what hunks say listed
  below.
- **Patch-level** (bug fixes that make the code match the document): a `focus` pattern mask
  now masks; a dead renderer can no longer hold a run until the job times out; a mutant whose
  run throws counts as escaped instead of ending the self-test; the scorecard's PR links point
  at the monorepo; the scheduled synthetic monitor (`post-deploy.yml`) stands down, green,
  with a notice, when no release run has kept a `release-report` to compare production with.

## What is new

- **Kept reports.** `harness reports keep` copies a run's `report.json`, `report.md` and
  `report.html` into `<store>/reports/<ranAt>-<mode>/` and lists it in
  `<store>/reports/index.json`. The nightly keeps the last 14 nights on the `noise` branch;
  `release.yml` keeps each judged candidate on `release-records`. Same branches, same jobs,
  same permissions. [../contract.md](../contract.md#kept-reports).
- **The scorecard.** `harness scorecard` turns one `report.json` into a 0-100 score with every
  deduction, the A/A normalness, EARS Rule to diffs to PRs (links to the monorepo's pull
  requests), and at most five pages to test by hand. `reports keep` writes it beside each kept
  report and its headline into `index.json`. Informational: it never changes a verdict or an
  exit code.
- **Main to RC.** `main-preview.yml` runs release mode every day with production on side a and
  main's newest signed images on side b, against main's claims, and keeps each forecast on the
  `main-preview` branch (its `publish` job holds `contents: write`, the one new write scope).
  A forecast, never a gate: it never writes `release-records`, so post-deploy cannot mistake it
  for a judged candidate. `harness preview resolve` and `--force` decide what it judges.
  [../contract.md](../contract.md#main-to-rc).
- **Report pages.** `pages.yml` publishes the kept reports of all three branches to
  [tutors-sdk.github.io/tutors-release-harness](https://tutors-sdk.github.io/tutors-release-harness/),
  rebuilt after every workflow that keeps a report (`pages: write`, `id-token: write`; writes
  no branch).
- **One recorded copy of third-party hosts.** What the apps load in the browser from Google
  Fonts, Iconify and `cdn.jsdelivr.net` is fetched once, recorded without its volatile
  headers, and served from the record on both sides and in later runs
  (`src/collectors/third-party-cache.ts`, `HARNESS_THIRD_PARTY_CACHE_DIR`). Every workflow job
  that runs journeys restores and saves that directory with `actions/cache`. The record never
  refreshes by itself: see [the user guide](../user-guide/01-concepts.md#normalising-and-masks)
  for how to pick up a changed font or icon.
- **Journeys cannot hang a run.** A journey has a 3-minute deadline and ends at once when its
  renderer crashes; every Playwright call without its own timeout gets 30 s.
- **Screenshot hunks say where.** A failing `screenshot` hunk's summary gives the box around
  every differing pixel.

## New flags, environment variables, report fields

| Kind | Since 1.5.0 |
| --- | --- |
| Stable commands and flags | none |
| Non-stable commands and flags | `harness reports keep`, `harness scorecard`, `harness preview resolve`, `--force` |
| Environment | `HARNESS_THIRD_PARTY_CACHE_DIR` (default `<HARNESS_HOME>/third-party-cache`) |
| `report.json`, `noise-status.json`, dispatch payloads | none |
| Exit code | unchanged |
| Artifacts | `main-preview-report` (`main-preview.yml`, 14 days) |
| Branches | `main-preview` (new); `noise` and `release-records` also carry `reports/` |
| Workflows | `main-preview.yml` (Main to RC), `pages.yml` (Report pages); every job that runs journeys restores and saves the third-party record (`thirdPartyCache` in `workflows.json`) |

### Behaviour that changes without a flag or field

- A journey that fails on both sides makes a noise run DEGRADED (verdict `warn`, `degraded` in
  `noise-status.json`), whether or not verification is required; any other mode names such a
  journey in its `reasons`.
- `image-manifest`: when a side's image was built here from a monorepo ref, a difference in a
  label the publishing pipeline stamps (`title`, `description`, `url`, `source`, `vendor`,
  `documentation`, `authors`) is an `info` hunk, not a failure. Every other label still fails.
- A `focus` pattern mask rewrites each keyboard stop like the ARIA snapshot; before, it loaded
  but changed nothing.
- A third-party font, icon or stylesheet can no longer arrive on one side only; a URL never
  recorded whose host is unreachable is answered 504, alike on both sides.
- A streamed media request (a `video/*` or `audio/*` body, or any `206`) is compared by whether
  it was made, its status and its type, not by how many times.
- The scheduled post-deploy monitor no longer fails every run while there is no recorded
  release: it stands down with a notice in the run summary. A `deployed` dispatch or a
  `recorded_run_id` without a recording still fails.
- As always, a report is comparable only with one of the same harness version.

## Pinning and tags

A `repository_dispatch` runs the harness on this repository's default branch; the caller does
not pick a version. Every report carries `harness.version` and `harness.gitSha`, so what
judged a run is always recorded. Released versions are marked by the tag `v1.5.0` (and
`v<version>` for later ones), created on `main` by a maintainer, never by a workflow
([../contract.md](../contract.md#versions)).
