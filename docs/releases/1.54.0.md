# Harness 1.54.0 (contract 1.54.0)

Which kind of build serves production. A **minor**. Part of the harness hardening plan (production-readiness additions, tranche 1, item A2).

## Why

Post-deploy already asked production's reader which commit it serves (`/_app/version.json`, `/version`). The 16.2.2 5 Whys found the real gap was a level down: the same commit, built twice, by two different builders. tutors.dev is built by Netlify from source, while the Gate judges the quay.io images. "production build: match" said the commit was right and nothing about whether the thing serving it was the thing judged.

## What changed

- `src/modes/production-build.ts`: the same two requests now also keep the `server` and `x-nf-request-id` headers, and `/version`'s `buildId`, `builtAt` and `digest` (or `imageDigest`) when it sends them. `productionBuild.servingBuild` is `{ kind, id?, builtAt?, evidence }`:
  - `netlify`: Netlify's `server` or `x-nf-request-id` header answered; `id` is `/version`'s `buildId` when sent.
  - `image`: `/version` names an image digest; `id` is that digest.
  - `unknown`: neither.
- `report.md` and `report.html` show it as a row of the Production build table.
- `deployment.record` carries the release record's `pinned`. When the deployment was checked against a record whose `pinned` is true and Netlify serves production, `reasons` gains `PRODUCTION IS NOT THE PINNED ARTEFACT` and a PASS becomes a WARN, as a digest that differs already does. A FAIL stays a FAIL.

## What it needs from the monorepo

`/version` carrying `buildId` (Netlify's `DEPLOY_ID` at build time, or the image digest once served from a container) and `builtAt`. Until then a Netlify build is still told apart by its headers, with no id.

## Not done

The plan also said to write `servingBuild` to the release record. Post-deploy reads the record and never writes it (release mode owns it), so it is in `report.json` only; the A4 served-artefact score (tranche 2) reads it from there.
